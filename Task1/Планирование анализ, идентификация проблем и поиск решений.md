# Планирование: анализ, идентификация проблем и поиск решений (Task1)

## Контекст и допущения

* Текущая боль бизнеса: растущая просрочка заказов, потеря B2B-контрактов, деградация UX операторов в MES.
* Производство как таковое не является узким местом (мощности позволяют x2 рост); проблема в ИТ-контуре: создание/прохождение заказа, расчёт стоимости, согласование, назначение оператору, отображение очереди.
* Интеграция CRM↔MES построена на RabbitMQ (несколько топиков). Для B2C магазин хранит «истину» о заказе в Shop DB, CRM API напрямую работает с Shop DB.
* Для B2B партнёры вызывают MES API; заказ в CRM создаётся через сообщение из очереди (асинхронно).
* Каждый сервис и БД - в одном экземпляре; горизонтального масштабирования и репликации чтения фактически нет.

## 1) Проблемные места (существующие и потенциальные)

### 1.1. Сквозной процесс заказа «не наблюдаем» и не управляем

* Нет единого «таймлайна» заказа: где он сейчас, кто владелец шага, какие переходы статусов были, что было ретраено/отвалилось.
* Команда узнаёт об инцидентах из жалоб (нет SLO/SLA, алертов, корреляции по order_id).

**Риск:** невозможно быстро локализовать причину «зависания», исправления делаются вслепую, продолжительность инцидентов растёт.

### 1.2. Потери/дубликаты сообщений и неконсистентность данных между системами

* Заказ проходит через несколько систем (Shop DB ↔ CRM API ↔ RabbitMQ ↔ MES API ↔ MES DB), но не описаны гарантии доставки, идемпотентность, порядок обработки.
* В B2B-сценарии создание заказа в CRM зависит от сообщения из очереди → при сбое/задержке сообщения партнёр видит «заказ пропал».
* CRM API напрямую читает/пишет Shop DB → сильная связность и высокая цена изменений схемы/запросов.

**Риск:** «зависшие» заказы из-за потерянных/дублированных событий и несогласованности статусов (особенно при ретраях и деградации брокера/БД).

### 1.3. Расчёт стоимости тяжёлый и, вероятно, смешан с онлайн-контуром

* Расчёт цены зависит от полигональности 3D и может занимать до 30 минут.
* Если расчёт выполняется в том же контуре, что обслуживает REST-запросы и пишет в БД, то он:

  * блокирует воркеры, держит ресурсы, ухудшает latency остальных операций,
  * создаёт «хвост» по очереди задач (эффект домино),
  * повышает вероятность timeouts у партнёров и повторов запросов (дубликаты).

**Риск:** при росте объёма заявок система превращается в «очередь из долгих вычислений» без контроля.

### 1.4. Деградация MES-дашборда «список заказов по статусам»

* Пагинация и фильтр по статусу не помогли → причина обычно в:

  * тяжёлых запросах (JOIN/AGG) по большой таблице,
  * отсутствии нужных индексов / неправильной сортировки (ORDER BY по времени + фильтр по статусу),
  * конкуренции за ресурсы БД с записью статусов и расчётами,
  * отсутствии специализированной read-модели под «самые новые заказы».
* Бизнес-требование: операторам критично видеть *самые новые* и быстро «забрать в работу» (соревновательная механика).

**Риск:** операторы работают медленнее, растёт время до старта производства → увеличивается просрочка.

### 1.5. Низкая отказоустойчивость и масштабируемость инфраструктуры

* Один инстанс на сервис → SPOF, нет возможности безболезненно масштабировать «горячую» часть.
* БД по одному инстансу и на чтение, и на запись → рост нагрузки быстро упирается в CPU/IO/коннекты.
* Нет описанного механизма backpressure при перегрузке (очереди, лимиты, деградация функциональности).

**Риск:** линейный рост заказов приведёт к нелинейной деградации (латентность → ретраи клиентов → ещё больше нагрузка).

### 1.6. Внешний API без контрактов по нагрузке и защите от злоупотреблений

* Нет упомянутых: rate limits, quotas, API-ключей с ограничениями, WAF, ограничения размера 3D, управление ретраями.
* При деградации партнёры начинают «дожимать» систему повторными запросами.

**Риск:** партнёры (или злоумышленники) способны перегрузить MES API и сорвать B2C.

### 1.7. Процессы поставки изменений тормозят реакцию на бизнес-инциденты

* Ручной деплой release/prod, E2E вручную и «блокирующее QA» → частые месячные задержки релиза.
* С ростом нагрузки нужны быстрые безопасные хотфиксы, но процесс этому противоречит.

**Риск:** даже найденные исправления доезжают в прод слишком поздно; бизнес теряет деньги в «окне ожидания».

### 1.8. Работа с 3D-файлами: стоимость, безопасность, эксплуатация

* Отсутствуют лимиты/валидация на входе (размер/формат/полигональность), lifecycle-политики в S3, антивирус/сканирование.
* Сложные модели могут занимать ресурсы расчёта «бесконечно», а хранение - раздуваться.

**Риск:** эксплуатационные расходы растут, повышается вероятность инцидентов и уязвимостей.

## 2) Инициативы для устранения проблем (что нужно сделать)

Ниже - инициативы, сгруппированные по горизонту. Формулировки - «что делаем» + «какой эффект».

### 2.1. Срочные (0–4 недели): стабилизация и прозрачность

1. **Согласовать SLO/SLA и критические user journeys**

   * B2C: SUBMITTED → PRICE_CALCULATED → MANUFACTURING_APPROVED → MANUFACTURING_STARTED → SHIPPED
   * B2B: запрос партнёра → расчёт → создание заказа в CRM → дальнейшие статусы
2. **Внедрить базовую наблюдаемость (метрики + централизованные логи)**

   * RPS/latency/error rate по API; загрузка CPU/RAM; коннекты БД; метрики RabbitMQ (in-flight/DLQ).
3. **Быстрый performance-разбор MES дашборда**

   * EXPLAIN/pg_stat_statements; индексация под фильтр+сортировку; ограничить выборку; убрать тяжёлые агрегации из онлайн-запроса.
4. **Ограничить вредную нагрузку на входе**

   * rate limit для внешнего API, квоты по ключу; лимиты размера/типа 3D; таймауты и понятные ответы клиентам.
5. **Описать и включить базовые гарантии RabbitMQ**

   * durable queues/exchanges, publisher confirms, DLQ, ретраи с backoff; мониторинг очередей.

### 2.2. Среднесрочные (1–3 месяца): устранение корневых причин

6. **Разделить «приём заказа/статусы» и «тяжёлый расчёт цены»**

   * Вынести расчёт цены в асинхронный пайплайн: очередь задач + воркеры (масштабируемые).
   * MES API становится «тонким» (принимает запрос, кладёт задачу, отдаёт ticket/status; либо async callback/webhook для партнёров).
7. **Сделать обработку событий надёжной: outbox + идемпотентность**

   * Для всех событий заказа: гарантированная публикация из транзакции (outbox) и идемпотентные consumer’ы (dedup key = order_id+event_type+version).
   * Ввести версионирование статусов/переходов (optimistic locking) и контроль допустимых переходов.
8. **Разорвать прямую связку CRM API ↔ Shop DB (поэтапно)**

   * Минимально: выделить «Order Service» как владелец данных о заказе (единый контракт), CRM/Shop работают через него.
   * Либо: перейти на event-driven синхронизацию и read-модель для CRM, чтобы CRM не писала напрямую в Shop DB.
9. **Сделать read-модель для очереди заказов в MES**

   * Отдельное хранилище/таблица/индекс под «последние заказы по статусу», обновляемое событиями (CQRS-подход).
   * Возможные реализации: materialized view + частое обновление, отдельная таблица «order_feed», Redis sorted set, OpenSearch (если нужен поиск/фильтры).

### 2.3. Стратегические (3–6 месяцев): масштабирование и скорость поставки

10. **Горизонтальное масштабирование сервисов и БД**

    * Несколько инстансов API за балансировщиком; отдельные worker-пулы для расчётов.
    * Read-реплики PostgreSQL + pooling (PgBouncer), раздельные параметры для OLTP и «ленты».
11. **Контейнеризация и переход к Kubernetes (MVP → prod-ready)**

    * Начать с MES API + pricing workers + RabbitMQ (как managed или в кластере), затем остальные.
    * Автоскейлинг по метрикам очереди/CPU.
12. **Ускорение релизного процесса**

    * Автотесты (smoke + критичные E2E), pipeline с обязательным прогоном, быстрые hotfix-ветки.
    * Канареечные/blue-green выкладки, чтобы не блокировать бизнес месяцами из-за ручного QA.
13. **Управление файлами 3D как продуктом**

    * Пресайн-URL, lifecycle/retention, квоты, «ранняя оценка сложности» (полигональность) и отказ/упрощение до расчёта.
14. **Оргмеры и найм под узкие места**

    * QA Automation (чтобы убрать ручную блокировку релизов).
    * Доп. C#/backend инженер под MES и расчётный пайплайн.
    * Частично/по необходимости: SRE/DevOps поддержка (K8s, наблюдаемость, CI/CD), DBA-консультация на настройку PostgreSQL.

## 3) Приоритизация инициатив (почему так)

Критерии:

* **Снижение просрочки и потери заказов** (бизнес-ущерб прямо сейчас).
* **Снижение MTTR** (время поиска причины и восстановления).
* **Снятие технических ограничений роста** (масштабирование и backpressure).
* **Срок до эффекта** (что даёт результат быстро).

### Очередность (выполнять параллельно, но с ясным главным фокусом)

1. Observability + SLO/SLA (п.1–2) - без этого остальные изменения будут «стрельбой вслепую».
2. MES дашборд: DB performance + read-оптимизация (п.3) - напрямую влияет на просрочку, потому что задерживает старт производства.
3. Ограничение внешней нагрузки + базовые гарантии RabbitMQ (п.4–5) - чтобы остановить лавинообразные ретраи партнёров и падения.
4. Вынесение расчёта цены в асинхронный пайплайн (п.6) - главный рычаг масштабирования без деградации API.
5. Надёжная событийная модель: outbox/идемпотентность/версии статусов (п.7) - устраняет «пропажи» и «зависания».
6. Разрыв прямых DB-зависимостей и формирование «Order Service»/контрактов (п.8) - снижает связность и риски изменений.
7. Горизонтальное масштабирование, реплики БД, K8s, ускорение релизов (п.10–12) - закрепляет устойчивость и скорость поставки.

## 4) Целевая архитектура через 6 месяцев (как выглядит «здоровая» система)

### Сквозной поток заказа

* Все участники (B2C магазин, CRM, MES, внешние партнёры) работают через чёткий контракт «заказ/статус/файл».
* Переходы статусов контролируются (версионирование, допустимые переходы, аудит).
* События доставки надёжны: outbox, идемпотентные consumer’ы, DLQ и ретраи с backoff.

### Производительность и масштабирование

* Тяжёлый расчёт цены - **асинхронный**: очередь задач + масштабируемые pricing workers.
* MES операторский интерфейс читает «ленту заказов» из read-модели (быстрое получение последних заказов).
* API и воркеры масштабируются горизонтально; есть backpressure (лимиты, очереди, деградация не критичных функций).

### Эксплуатация

* Наблюдаемость «из коробки»: метрики, логи, трассировка, дашборды, алерты; измеряем SLO по заказам и по API.
* CI/CD обеспечивает частые безопасные релизы (автотесты + канареечные выкладки).
* Управление 3D: лимиты, ранняя оценка сложности, lifecycle, безопасность.

### Если можно сделать только 3 инициативы за полгода - что выбрать и почему

### Выбор 1: Observability + SLO/SLA (метрики/логи/трейсы + алерты)

**Почему:** это сокращает MTTR, даёт управляемость и позволяет доказуемо улучшать просрочку. Без наблюдаемости вы не сможете подтвердить, что именно улучшилось и где деградация.

### Выбор 2: Асинхронный расчёт цены + масштабируемые воркеры

**Почему:** это главный источник «длинных хвостов» и деградации под ростом. Разделение онлайн-API и долгих вычислений даёт линейное масштабирование и убирает таймауты/ретраи партнёров.

### Выбор 3: Надёжность событий и состояния заказа (outbox + идемпотентность + контроль статусов)

**Почему:** это напрямую бьёт по «пропавшим»/«зависшим» заказам и репутации. В условиях роста и ретраев без идемпотентности система неизбежно разваливается.
