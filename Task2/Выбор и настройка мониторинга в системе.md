# Выбор и настройка мониторинга в системе (Task2)

## 1. Контекст и цели

После открытия внешнего API (B2B) Яндекс.Метрика перестала отражать реальную нагрузку и качество сервиса: значимая часть заказов создаётся и живёт без браузерного трафика, а проблемы проявляются как «потерянные/зависшие» заказы и деградация MES.

**Цель мониторинга** — получать измеримую картину работы системы (техническую и процессную), чтобы:
- обнаруживать сбои/деградации *до* жалоб клиентов;
- быстро локализовать, где «завис» заказ (API / очередь / БД / расчёт цены);
- управлять масштабированием и ресурсами (CPU/RAM/коннекты/очереди);
- иметь цифры для SLA/SLO (и для B2C, и для партнёров B2B).

**Окружения:** dev / release / prod. Мониторинг в прод — обязателен; dev/release — укороченный, но совместимый по метрикам/лейблам.

---

## 2. Мотивация

### 2.1. Бизнес-эффект
- **Снижение потерь заказов и просрочек.** Основной ущерб сейчас — не «производство не справилось», а сбой ИТ-процесса (сообщение не доставилось / расчёт цены не завершился / статус не обновился / оператор не видит новый заказ).
- **Удержание B2B клиентов.** Для API-пользователей нужна прогнозируемость и прозрачность: ошибки/таймауты должны быть видны и устранимы быстро, иначе они уходят.
- **Управляемое масштабирование при линейном росте нагрузки.** Наблюдаемость позволяет заранее увидеть насыщение (очереди, БД, CPU) и расширять мощности планово, а не в пожарном режиме.
- **Сокращение времени расследований.** Сейчас инциденты разбираются «со слов клиента». Мониторинг уменьшит MTTR (время восстановления) и количество повторяющихся проблем.

### 2.2. Технический эффект
- единые дашборды по API/очередям/БД/инфре;
- алерты по ошибкам, задержкам, росту очередей и насыщению;
- база для дальнейшего трейсинга и SLO-управления (Task3).

---

## 3. Выбор подхода к мониторингу

Используем смешанный подход — по типу компонента:

1) **API (Shop API / CRM API / MES API)** — **RED**:  
- **Rate** (нагрузка), **Errors** (ошибки), **Duration** (латентность).  
Причина: API — пользовательский контракт (и B2C, и B2B).

2) **Инфраструктура сервисов и VM/контейнеров** — **USE**:  
- **Utilization** (утилизация), **Saturation** (насыщение), **Errors** (ошибки).  
Причина: позволяет заранее видеть, где закончится ресурс.

3) **Базы данных и RabbitMQ** — **Четыре золотых сигнала** (latency/traffic/errors/saturation)  
Причина: эти компоненты часто становятся бутылочным горлышком и «скрытой» причиной деградации.

## 4. Метрики: что отслеживаем и зачем

Ниже указаны метрики из списка задания (и дополнительные — где это критично для реальной диагностики).

### 4.1. RabbitMQ (очереди и доставка событий)

**1. Number of dead-letter-exchange letters in RabbitMQ**  
- **Зачем:** прямой индикатор потери/невозможности обработки сообщений (заказы/статусы уходят в DLQ → «зависания»).  
- **Лейблы:** `env`, `vhost`, `queue`, `exchange`, `routing_key`, `producer_service`, `consumer_service`, `reason` (если доступно).

**2. Number of message in flight in RabbitMQ**  
- **Зачем:** показывает текущую нагрузку и «хвост» обработки; рост = потребители не успевают.  
- **Лейблы:** `env`, `queue`, `consumer_group` (если есть), `message_type`.

**Дополнительно (рекомендуется):**
- `queue_depth` (сколько сообщений в очереди) и `message_age_seconds` (возраст самого старого сообщения) — лучше отражают «зависание», чем только in-flight.
- `publish_rate/ack_rate/redelivered_rate` — чтобы отличать реальный рост заказов от ретраев/дубликатов.

---

### 4.2. API: Shop API / CRM API / MES API (пользовательский контракт)

**3. Number of requests (RPS) for internet shop API**  
**4. Number of requests (RPS) for CRM API**  
**5. Number of requests (RPS) for MES API**  
- **Зачем:** базовая нагрузка; рост нужен для планирования масштабирования и расследования пиков (например, партнёр «льёт» ретраи).  
- **Лейблы:** `env`, `service`, `method`, `route` (шаблон пути), `status_code_family` (2xx/4xx/5xx), `client_type` (B2C/B2B/internal).

**6-8. Number of requests (RPS) per user for * API**  
- **Зачем:** выявление аномалий/злоупотреблений (один API-клиент перегружает систему), отделение B2B от B2C.  
- **Лейблы:**  
  - для B2C: `user_id_hash` (только хэш), `session_id_hash`;  
  - для B2B: `api_client_id` / `partner_id` (не PII), `contract_tier` (если есть).  
  - общее: `route`, `method`.

**19-21. Response time (latency) for * API**  
- **Зачем:** основной индикатор деградации; обязательно хранить percentiles (p50/p95/p99).  
- **Лейблы:** `env`, `service`, `route`, `method`, `client_type`, `status_code_family`.

**25-27. Number of HTTP 200 for * API**  
**28-30. Number of HTTP 500 for * API**  
- **Зачем:** качество API; 5xx — алерт; 2xx — контроль объёма успешных операций.  
- **Лейблы:** `env`, `service`, `route`, `client_type`, `api_client_id` (для B2B), `error_class` (для 5xx, если можно извлечь).

**32-34. Number of simultaneous sessions for * API**  
- **Зачем:** полезно для оценки нагрузки фронта и пиков активностей; для MES важно «сколько операторов одновременно».  
- **Лейблы:** `env`, `service`, `role` (customer/seller/operator/api_user), `tenant` (B2C/B2B).

**35-40. Kb transferred/ provided for * API**  
- **Зачем:** контроль сетевой нагрузки и «тяжёлых» операций (например, загрузка 3D). Важнее для Shop API (upload) и MES API (download для расчёта).  
- **Лейблы:** `env`, `service`, `route`, `client_type`, `content_type`.

**Дополнительно (критично для кейса):**
- `price_calculation_duration_seconds` (время расчёта стоимости) + `price_calc_success/fail` — иначе не понять, где теряется время 2-30 минут.
- `3d_upload_size_bytes` и `3d_model_complexity` (полигональность, если можно измерить до расчёта) — для управления «тяжёлыми» моделями.

---

### 4.3. Ресурсы сервисов (VM/контейнеры)

**9-11. CPU % for * API**  
- **Зачем:** утилизация CPU и поиск насыщения (рост latency при CPU-сатурации).  
- **Лейблы:** `env`, `service`, `instance_id`.

**12-14. Memory Utilisation for * API**  
- **Зачем:** риск OOM, GC-паузы (для JVM), деградация.  
- **Лейблы:** `env`, `service`, `instance_id`.

**Дополнительно (рекомендуется):**
- `thread_pool/worker_pool` метрики (активные потоки, очередь задач) — особенно если расчёт цены идёт в MES API.
- `http_server_inflight_requests` — показывает очередь запросов внутри сервиса.

---

### 4.4. Базы данных PostgreSQL (Shop DB и MES DB)

**15-16. Memory Utilisation for * db instance**  
- **Зачем:** индикатор давления на память/кэш; падение производительности при нехватке RAM.  
- **Лейблы:** `env`, `db` (shop/mes), `instance_id`.

**17-18. Number of connections for * db instance**  
- **Зачем:** исчерпание коннектов — типичная причина «всё тормозит» и роста 5xx.  
- **Лейблы:** `env`, `db`, `app_service` (shopApi/crmApi/mesApi), `pool` (если выделяется), `state` (active/idle).

**23-24. Size of * db instance**  
- **Зачем:** планирование диска/стоимости, контроль роста таблиц заказов и индексов.  
- **Лейблы:** `env`, `db`.

**Дополнительно (обязательно для диагностики):**
- `db_query_duration_seconds` (p95/p99) по ключевым запросам: список заказов MES, смена статуса, выборка по статусу/датам.  
- `locks_count`, `deadlocks_total`, `slow_queries_count` — частые причины деградации «дашборда» MES.

---

### 4.5. S3-хранилище 3D-файлов

**22. Size of S3 storage**  
- **Зачем:** контроль затрат, прогноз исчерпания квот, качество lifecycle-политик.  
- **Лейблы:** `env`, `bucket`, `storage_class`.

**Дополнительно (рекомендуется):**
- `s3_requests_total` и `s3_errors_total` (4xx/5xx) — иначе сложно отличить «MES не считает» из-за S3 от проблем в API.

---

### 4.6. Бизнес-метрики процесса заказа (добавляем поверх техметрик)

Эти метрики не из списка, но они напрямую отражают проблему «заказ завис/просрочен».

Рекомендуемый минимум:
- `orders_created_total{channel=B2C|B2B}`  
- `orders_in_status{status=...}` — количество заказов по статусам.
- `order_status_transition_total{from,to}` — контроль корректности переходов.
- `order_lead_time_seconds{from,to}` — время прохождения ключевых этапов, percentiles.
- `stuck_orders_total{status,threshold}` — сколько заказов «в статусе > X минут/часов/дней».

Ключевые SLO-кандидаты:
- `SUBMITTED → PRICE_CALCULATED`: p95 ≤ 30 минут (учитывая «тяжёлые» модели).  
- `MANUFACTURING_APPROVED → MANUFACTURING_STARTED`: p95 ≤ 24 часа (операторская очередь).  
- `MANUFACTURING_STARTED → SHIPPED`: по бизнес-нормативу производства/логистики.

## 5. Дашборды и алерты (минимально достаточный набор)

### 5.1. Дашборды
1) **API Overview (по сервисам):** RPS, p95/p99 latency, 4xx/5xx, top routes, bytes in/out.  
2) **RabbitMQ:** глубина очередей, in-flight, DLQ, возраст сообщений, publish/ack rates.  
3) **DB:** connections, p95 query time, locks/deadlocks, размер БД/таблиц, CPU/RAM инстанса.  
4) **MES Operations:** «лента» новых заказов, время ответа эндпоинта списка заказов, p95 по фильтрам, ошибки.  
5) **Order Flow (бизнес):** время между статусами, доля заказов в SLA, количество stuck-заказов.

### 5.2. Алерты (стартовые пороги, уточняются по данным 1-2 недель)
- **DLQ > 0** (критический) — немедленный алерт: сообщения потеряны/не обработаны.  
- **RabbitMQ message_age_seconds p95 > 15 минут** (критический) — потребители не успевают.  
- **API 5xx rate > 2% за 5 минут** (высокий) и **>5%** (критический).  
- **API latency p95**:
  - Shop/CRM: > 1 сек за 10 минут (высокий), > 3 сек (критический)  
  - MES: > 2 сек за 10 минут (высокий), > 5 сек (критический)
- **DB connections > 80% max** 10 минут (высокий), > 90% (критический).  
- **CPU > 70% 10 минут** или **Memory > 80% 10 минут** на сервисе (высокий).  
- **Stuck orders**:
  - доля заказов `SUBMITTED→PRICE_CALCULATED > 30 минут` > 5% за час (высокий), > 10% (критический).

## 6. План действий (высокоуровневое ТЗ)

### 6.1. Платформа мониторинга
1) Выбрать и развернуть time-series хранилище и визуализацию:  
   - вариант A: **Managed Prometheus / Yandex Monitoring + Grafana** (минимум эксплуатации);  
   - вариант B: **Prometheus + Alertmanager + Grafana** (самостоятельно в облаке, 2 VM минимум).
2) Настроить единые лейблы: `env`, `service`, `instance`, `version`, `client_type` (B2C/B2B/internal).

### 6.2. Сбор метрик
3) Подключить метрики сервисов:
   - Spring Boot: Actuator + Micrometer (Prometheus endpoint).
   - .NET (MES API): prometheus-net / OpenTelemetry metrics exporter.
4) Сбор инфраструктуры:
   - node_exporter (VM), при контейнеризации — cAdvisor/kube-state-metrics.
5) RabbitMQ exporter + конфигурация DLQ и метрик очередей.
6) PostgreSQL exporter + включение статистики запросов (pg_stat_statements) в prod.
7) Метрики S3 (через облачный мониторинг/экспортер, в зависимости от выбранного варианта).

### 6.3. Дашборды и алерты
8) Собрать 5 дашбордов (см. раздел 5.1) в Grafana, закрепить ответственность владельцев.  
9) Настроить алерты и маршрутизацию уведомлений (почта/мессенджер) + уровни критичности.  
10) Ввести процесс: еженедельный обзор метрик + корректировка порогов + список топ-3 узких мест.

### 6.4. Бизнес-метрики заказов
11) Определить «источник правды» для событий заказа (минимально: агрегатор на базе текущих БД/очередей).  
12) Реализовать экспорт метрик по статусам (например, фоновой задачей раз в 1-5 минут) и построить дашборд Order Flow.

## 7. Доп. задание: показатели насыщенности и реакция системы

Насыщенность — это состояние, когда ресурс ещё «не упал», но уже не обеспечивает требуемое качество (растёт latency/ошибки/очереди).

### 7.1. Показатели и пороги
**RabbitMQ**
- `message_age_seconds p95 > 15 мин` или `queue_depth > 10 000` (10 минут).  
**Почему:** это прямой индикатор, что обработчики не успевают, а заказы начнут «висеть».  

**MES API**
- CPU > 70% (10 минут) или latency p95 > 2 сек (10 минут).  
**Почему:** MES — узкое место по UX операторов; деградация ведёт к задержке старта производства.

**PostgreSQL**
- connections > 80% лимита (10 минут) или p95 query time по ключевым запросам > 500 мс.  
**Почему:** исчерпание коннектов и медленные запросы быстро дают каскадную деградацию API и очередей.

**S3**
- storage > 80% квоты или рост > 10%/неделя без планов на очистку.  
**Почему:** риск упереться в лимиты/стоимость и получить побочные инциденты.

**Процесс заказа**
- `SUBMITTED→PRICE_CALCULATED > 30 минут` у > 5% заказов за час.  
**Почему:** это центральная бизнес-боль (обещали 2-3 минуты, иногда 30 минут — нужен контроль хвоста).

### 7.2. Что делать при превышении
Уровни реакции:

**Warning (высокий риск в течение часов):**
- автоматически создать тикет (Jira) с графиками и текущими значениями;
- уведомить ответственного инженера/DevOps;
- включить «защитный режим» (если реализовано): rate limit для B2B, снижение частоты тяжёлых запросов (дашборды/агрегации).

**Critical (срыв SLA/потери заказов):**
- эскалация дежурному (Pager/звонилка/экстренный канал);
- оперативное расширение мощностей: добавить инстанс API за балансировщиком, увеличить size DB, поднять воркеры расчёта (если выделены);
- при необходимости — временно ограничить приём новых B2B-заказов или перевести партнёров на деградационный режим (например, «расчёт принят, результат позже»).

## 8. Результат внедрения (критерии успеха)

Через 2-4 недели после внедрения минимумов мониторинга:
- есть дашборды по API/очередям/БД и алерты по DLQ/5xx/latency/коннектам;
- можно ответить на вопросы: *где заказы зависают* и *какая компонента стала узким местом*;
- MTTR по типовым инцидентам уменьшается (целевой ориентир: в 2-3 раза);
- появляется база для трейсинга (Task3) и управляемого масштабирования.
