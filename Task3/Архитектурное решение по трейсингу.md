# Архитектурное решение по трейсингу (Task3)

## 1. Вводные данные

В системе «Александрит» заказы часто:
- оказываются в «непонятном» состоянии (статусы расходятся между системами);
- «зависают» на шаге (не меняются длительное время);
- теряются/дублируются из‑за проблем интеграции через RabbitMQ и ретраев клиентов.

Нужно внедрить распределённый трейсинг, чтобы по **order_id** команда могла восстановить цепочку действий:
HTTP-запросы, публикации/потребления сообщений, обращения к БД и S3 — и увидеть точку деградации.

---

## 2. Системы, которые покрываем трейсингом (и где заказ может «сломаться»)

### 2.1. Обязательное покрытие (MVP)
1) **Shop API (Spring Boot)**  
- создание/обновление заказа, загрузка 3D, перевод в `SUBMITTED`  
- точки сбоя: таймауты, 5xx, долгие операции, проблемы с S3

2) **CRM API (Spring Boot)**  
- подтверждение `MANUFACTURING_APPROVED`, публикация/получение событий  
- точки сбоя: потеря событий, рассинхрон статусов, долгие запросы в Shop DB

3) **MES API (C#)**  
- расчёт цены (`PRICE_CALCULATED`), назначение/статусы производства  
- точки сбоя: длительные вычисления, ретраи, конкуренция за ресурсы, медленный «дашборд» (список заказов)

4) **RabbitMQ** (паблишеры/консьюмеры в CRM и MES)  
- точки сбоя: DLQ, redelivered, задержки обработки, несоответствие routing_key/очередей

### 2.2. Рекомендуемое расширение
5) **PostgreSQL (Shop DB / MES DB)**  
- ключевые запросы: создание заказа, смена статуса, выборка списка заказов в MES  
- точки сбоя: блокировки, медленные запросы, нехватка коннектов

6) **S3-хранилище 3D**  
- upload/download для расчёта цены  
- точки сбоя: ошибки доступа, деградация latency

> UI (Vue/React) можно подключить позже (frontend tracing), но для текущей проблемы достаточно backend + messaging.

---

## 3. Какие данные должны попадать в трейсинг

### 3.1. Технические поля (стандарт)
- `trace_id`, `span_id`, `parent_span_id`
- `service.name`, `service.version`, `deployment.environment` (dev/release/prod)
- `http.method`, `http.route`, `http.status_code`, `net.peer.name`
- `db.system=postgresql`, `db.name`, `db.operation`, `db.statement` (желательно хэш/шаблон, без PII)
- `messaging.system=rabbitmq`, `messaging.destination` (exchange/queue), `messaging.rabbitmq.routing_key`, `messaging.operation` (publish/consume)
- `error=true`, `exception.type`, `exception.message` (с маскированием)

### 3.2. Бизнес‑корреляция (ключевое для расследований)
- `order.id` (обязательно)  
- `order.status.from`, `order.status.to` (на переходах)
- `order.channel` = `B2C | B2B`
- `api.client_id` (для B2B; без персональных данных)
- `customer.id_hash` (для B2C; строго хэш)
- `file.id` (идентификатор 3D), `file.size_bytes`
- `price.calc.polygons` (если вычисляется), `price.calc.duration_ms`, `price.calc.attempt`
- `outbox.id` / `event.id` (если используется outbox) и `message.id` (для дедупликации)

### 3.3. Правила нейминга спанов (чтобы это было удобно)
- HTTP: `HTTP {method} {route}` (например, `HTTP POST /orders/{id}/submit`)
- Messaging:
  - publish: `RMQ publish {exchange}:{routing_key}`
  - consume: `RMQ consume {queue}`
- БД: `DB {operation} {table}` (например, `DB SELECT orders_feed`)
- S3: `S3 GET/PUT {bucket}`

## 4. Мотивация

### 4.1. Зачем трейсинг в этой системе
- **Точка истины по заказу.** По `order.id` можно быстро понять, где заказ «застрял»: API, очередь, консьюмер, БД, S3 или вычисление.
- **Быстрая локализация инцидентов.** В связке HTTP + RabbitMQ без трейсинга сложно доказать, что именно потерялось и где.
- **Снижение MTTR.** Команда перестаёт расследовать «по рассказам пользователей» и переходит к фактам.

### 4.2. Метрики, на которые повлияет внедрение (3–5)
Технические:
1) **MTTR** (время восстановления) — должно снизиться, так как появляется наблюдаемая цепочка действий.  
2) **Error rate** по критическим операциям (submit order / calculate price / approve manufacturing).  
3) **p95/p99 latency** по ключевым эндпоинтам и консьюмерам очереди.

Бизнес:
4) **Доля «застрявших» заказов** (например, в `SUBMITTED` без `PRICE_CALCULATED` > X минут).  
5) **Доля нарушений SLA** по этапам (submit→price, approved→started, started→shipped).

## 5. Предлагаемое решение

### 5.1. Технологии и компоненты
- **OpenTelemetry** как единый стандарт сборки трейсов (SDK + автоинструментация).
- **OpenTelemetry Collector** (центральная точка приёма) — буферизация, сэмплинг, обогащение, экспорт.
- **Jaeger** как хранилище и UI для трейсов (подходит для MVP и прод при корректном хранении/ретенции).

Схема (новые компоненты выделены красным):
- `./alexandrite-tracing.puml`

### 5.2. Как обеспечиваем сквозную трассировку
1) **HTTP‑цепочки**  
- Автоинструментация на входе/выходе (Spring Boot + .NET).  
- Пропагация контекста через W3C Trace Context (`traceparent`, `tracestate`) по HTTP.

2) **RabbitMQ (критично для этого кейса)**  
- При публикации событий добавляем `traceparent`/`tracestate` и `baggage` (например, `order.id`) в headers сообщения.  
- Консьюмер извлекает контекст из headers и продолжает трейс (создаёт child‑span на обработку сообщения).  
- Для ретраев/ределивери фиксируем `message.redelivered`, `price.calc.attempt`, `event.id`.

3) **БД и S3**  
- Включаем instrumentation для Postgres и S3‑клиента, чтобы видеть вклад БД/S3 в latency и ошибки.

### 5.3. Сэмплинг и ретенция (чтобы не «утонуть» в данных)
- На старте: **head sampling** 10–20% для всего трафика + **100%** для ошибок и для операций расчёта цены.  
- Для расследований: возможность временно включить 100% sampling для конкретного `api.client_id` (B2B) или маршрута.
- Ретенция трейсов: 7–14 дней (по нагрузке), затем — удаление.

### 5.4. План внедрения по этапам
Этап 1 (быстро, 1–2 спринта):
- поднять OTel Collector + Jaeger, обеспечить сетевую доступность из сервисов;
- включить автоинструментацию HTTP в Shop API / CRM API / MES API;
- добавить `order.id` как span attribute в ключевых эндпоинтах;
- настроить пропагацию контекста через RabbitMQ headers.

Этап 2:
- добавить instrumentation к PostgreSQL и S3;
- стандартизировать нейминг спанов и атрибутов;
- описать «playbook расследования» (как искать заказ по `order.id`).

## 6. Компромиссы

- **Стоимость хранения и объём данных.** Трейсы (особенно при 100% sampling) могут быть дорогими → нужен сэмплинг и ретенция.
- **Не все проблемы решаются трейсингом.** Например, «заказ стоит неделю в статусе» — это скорее бизнес‑метрика процесса; трейсинг даст детали последнего шага, но нужны и метрики процесса (из Task2).
- **Сложность асинхронных цепочек.** При плохой дисциплине `event.id`/идемпотентности и ретраях будут «разветвления» — надо нормировать headers и атрибуты.
- **Проприетарные/внешние системы.** Если появятся внешние компоненты без OTel/контекста — будет «дырка» в трассировке.

---

## 7. Безопасность

- **Доступ к UI трейсов (Jaeger)** только сотрудникам компании по роли (Support/Dev/SRE), через SSO (OIDC) или корпоративный IAM.  
- **Сетевой периметр:** Jaeger UI и OTel Collector ingestion доступны только из внутренних подсетей/VPN/Zero‑Trust.  
- **PII‑политика:** в спаны не пишем персональные данные (ФИО/телефон/адрес). Только `order.id`, хэши идентификаторов и технические параметры.  
- **Аудит и ротация:** аудит доступа к observability, ротация ключей/паролей, разграничение прав (просмотр/администрирование).

## 8. Доп. задание: автоматический мониторинг процесса заказа и алертинг из данных трейсинга

Идея: получать **метрики из трейсов**, не дублируя ручную инструментализацию.

### 8.1. Как делаем метрики из трейсов
- В **OpenTelemetry Collector** включаем процессор **spanmetrics** (и при необходимости servicegraph), который:
  - строит метрики latency/error rate по выбранным спанам;
  - экспортирует их в Prometheus/Managed Monitoring.
- В Grafana строим дашборды и алерты по этим метрикам.

Схема с алертингом (новые элементы выделены зелёным):
- `./alexandrite-tracing-alerting.puml`

### 8.2. Примеры алертов (порог на старте, далее калибруется)
- **Ошибки:** `span_errors_rate` по спанам `HTTP POST /orders/*/submit`, `price.calculate` > 2% (5 минут).  
- **Деградация latency:** p95 длительность спана `price.calculate` > 30 минут (10 минут подряд).  
- **Очередь/консьюмер:** p95 длительность спана `RMQ consume order.events` > 5 секунд (10 минут) или резкий рост количества таких спанов.
- **Системный сигнал «заказы зависают»:** доля заказов без `PRICE_CALCULATED` спустя 30 минут (можно реализовать как отдельный «order watchdog» в Task2‑метриках, а в алерте добавлять exemplar/trace_id для примеров).

### 8.3. Реакция на алерты (процесс)
- P1/P2 уведомления в дежурный канал + тикет с ссылкой на Jaeger search по `order.id`/`trace_id`.  
- При перегрузке: временное ужесточение rate limit для B2B + скейлинг воркеров расчёта (когда появятся отдельные воркеры / Kubernetes).
