# Архитектурное решение по логированию (Task4)

## 1. Цель

Сделать так, чтобы инциденты и «странные» ситуации разбирались **по фактам** (логи + корреляция по заказу), а не «со слов клиента».  
Минимальный результат: по `order_id` можно быстро восстановить, что происходило с заказом в **Shop API / CRM API / MES API** и в интеграции через **RabbitMQ**.

---

## 2. Источники логов и что логируем

### 2.1. Системы, откуда собираем логи (минимум)
- **Shop API (Spring Boot)** - создание заказа, загрузка 3D, submit.
- **CRM API (Spring Boot)** - подтверждение производства, смена статусов, интеграция (publish/consume).
- **MES API (C#)** - расчёт цены, назначение заказа оператору, смена статусов, «дашборд заказов».
- **RabbitMQ** - системные логи брокера + события DLQ/повторы (по возможности через плагины/метрики).
- **PostgreSQL (Shop DB / MES DB)** - медленные запросы, ошибки соединений (не все SQL-логи, а именно полезные).
- **S3 storage** - ошибки доступа/загрузки/скачивания (на уровне SDK/клиента в сервисах).

> UI (Vue/React) можно подключить позже (frontend logging), основная боль сейчас - в backend + messaging.

### 2.2. Требования к формату
- **Структурные JSON‑логи** (одна запись = один JSON объект).
- Единый набор обязательных полей (см. ниже).
- Маскирование/запрет PII в логах.

### 2.3. Обязательные поля (в каждом событии)
- `ts` (ISO8601), `level`, `service`, `service_version`, `env` (dev/release/prod)
- `request_id` (на входе HTTP генерируем, если нет)
- `trace_id` / `span_id` (если есть трейсинг - отлично; если нет, можно внедрять поэтапно)
- `order_id` (если событие связано с заказом) - **ключ для расследований**
- `user_id_hash` (B2C, только хэш) / `client_id` (B2B, без персональных данных)
- `event_id` (идентификатор доменного события), `message_id` (RabbitMQ), `idempotency_key` (если используется)
- `http.method`, `http.route`, `http.status`, `duration_ms` (для API‑логов)
- `error.type`, `error.message` (с маскированием), `stacktrace` (только для ERROR)

---

## 3. Что логируем на уровне INFO (минимальный список)

Ниже - перечень **ключевых INFO‑событий**, которые должны быть в логах.

### 3.1. Shop API (INFO)
- `order_initiated` - создан заказ/корзина (если фиксируется в API).
- `file_uploaded` - `order_id`, `file_id`, `file_size_bytes`, `storage_bucket`.
- `order_submitted` - `order_id`, `channel` (B2C/B2B), `client_id`/`user_id_hash`.
- `outgoing_http_call` (опционально) - только агрегировано: target, duration, status.
- `db_write` (опционально) - факт записи (без содержимого).

### 3.2. CRM API (INFO)
- `manufacturing_approved` - `order_id`, кто подтвердил (`actor_id` без PII), время.
- `status_changed` - `order_id`, `from`, `to`.
- `event_published` - `event_id`, `order_id`, exchange/routing_key, `message_id`.
- `event_consumed` - `event_id`, `order_id`, `message_id`, `redelivered`.

### 3.3. MES API (INFO)
- `price_calc_started` - `order_id`, `attempt`, параметры модели (например, polygons_count если есть).
- `price_calc_finished` - `order_id`, `duration_ms`, результат (ok/fail), `price_amount` (если не чувствительно).
- `order_assigned` - `order_id`, `operator_id` (внутренний), время.
- `status_changed` - `order_id`, `from`, `to`.
- `orders_dashboard_query` - факт выполнения запроса списка заказов: фильтры, page/limit, `duration_ms`, rows_count.

### 3.4. RabbitMQ / DB (INFO, выборочно)
- RabbitMQ: `queue_binding_changed` (если бывает), `consumer_connected/disconnected` (если доступно).
- DB: `slow_query` (через pg_stat_statements + порог), `db_connection_pool_exhausted` (из приложения).

---

## 4. Уровни логирования (когда использовать)

- **INFO** - бизнес‑события и «сквозные» шаги процесса заказа (список выше).
- **WARN** - деградации без падения:
  - повторная доставка (`redelivered=true`), ретраи,
  - превышение ожидаемой длительности операции (например, `price_calc > 10 минут`),
  - частичная недоступность зависимостей (S3/DB) с успешным ретраем.
- **ERROR** - невозможность выполнить операцию:
  - не удалось сохранить заказ/статус,
  - ошибка публикации/консьюма сообщения,
  - расчёт цены завершился ошибкой.
- **DEBUG/TRACE** - только в dev/release и временно в prod на ограниченное время (через feature flag), чтобы не утопить систему.

---

## 5. Мотивация (почему бизнесу это нужно)

1) **Снижение MTTR**: быстрее локализуем причину «заказ пропал/завис».  
2) **Снижение нагрузки поддержки**: меньше ручных расследований и «переспросов» у клиента.  
3) **Снижение доли просроченных заказов**: быстрее находим узкие места (очереди/DB/расчёт).  
4) **Удержание B2B‑контрактов**: можно доказуемо разбирать спорные кейсы по логам/идентификаторам сообщений.  
5) **Качество релизов**: видно, что именно ломается после изменений (рост ERROR/WARN по конкретным маршрутам).

Метрики, на которые влияет:
- MTTR / время расследования;
- количество обращений в поддержку по «статус непонятен/заказ потерян»;
- доля заказов, застрявших на этапах (SUBMITTED без PRICE_CALCULATED и т.п.);
- error rate по критическим операциям;
- доля нарушений SLA производства/доставки из-за IT‑задержек.

---

## 6. Приоритет внедрения (логирование + трейсинг не делаем везде сразу)

**Порядок:**
1) **MES API + RabbitMQ** - максимальная концентрация проблем (долгий расчёт, очереди, статусы, операторский дашборд).  
2) **CRM API** - подтверждения и ключевая интеграция статусов.  
3) **Shop API** - источник заказов и загрузка 3D.

Причина: основная боль - «заказы застревают/теряются» и «MES тормозит», значит сначала покрываем самый проблемный контур.

---

## 7. Предлагаемое решение

### 7.1. Архитектура
- Все сервисы пишут **структурные JSON‑логи** в stdout (или в файл/журнал ОС).
- На каждом инстансе ставим лёгкий агент:
  - **Fluent Bit** (или Vector) - читает логи и отправляет в хранилище.
- Центральное хранилище логов:
  - **OpenSearch** (кластер/managed) + **OpenSearch Dashboards** для поиска и дашбордов.
- Интеграция с трейсингом:
  - пробрасываем `trace_id` в логи (через OTel или middleware), чтобы по логам переходить в Jaeger.

Диаграмма (новые компоненты выделены красным):
- `./alexandrite-logging.puml`

### 7.2. Индексация (минимум)
- Индекс/датастримы по схеме:
  - `logs-{env}-{service}-YYYY.MM.DD`
- Маппинг полей:
  - `order_id`, `event_id`, `message_id`, `trace_id` как keyword (для поиска).
  - `duration_ms` как number (для агрегаций).

---

## 8. Политика безопасности

- **PII запрещены** в логах (ФИО, телефон, адрес, email).  
- Разрешены только:
  - `order_id`, `client_id` (B2B), `user_id_hash` (B2C), внутренние id сотрудников.
- Маскирование ошибок:
  - `error.message` очищаем от персональных данных.
- Доступ:
  - RBAC: Support (read), Dev (read + limited manage), Admin (manage).
  - аудит доступа к логам (кто искал/смотрел).
- Сеть:
  - хранилище логов доступно только из внутренней сети/VPN.

---

## 9. Политика хранения (retention)

Рекомендуемый старт:
- **Hot** (полный поиск): 14–30 дней.
- **Warm/архив** (дешевле, реже нужен): до 90 дней (опционально).
- Автоудаление по ILM/retention policy.

Оценка объёма (упрощённо):
- средний размер JSON‑лога: 0.5–1.5 KB
- событий на один заказ: 20–50
- дневной объём ≈ `orders_per_day * events_per_order * avg_log_size`

---

## 10. Превращаем сбор логов в анализ: алерты и аномалии

### 10.1. Алертинг (минимально необходимый)
- В OpenSearch Dashboards/Grafana настраиваем:
  - рост `ERROR` по `service=mes-api` и `http.route=/price/calc` (условно) за 5–10 минут;
  - всплеск `WARN redelivered=true` по RabbitMQ‑консьюмерам;
  - рост `db_connection_pool_exhausted`;
  - рост `orders_dashboard_query.duration_ms` p95 (деградация UI операторов).

Реакция:
- уведомление в канал (почта/мессенджер) + тикет.
- ссылка на готовый saved search (фильтр по service + order_id/message_id).

### 10.2. Поиск аномалий (что ловим)
- резкий рост `order_submitted` (возможный DDoS/партнёр «сломался»);
- резкий рост `event_published` без соответствующих `event_consumed` (задержка/потеря консьюмера);
- массовые ошибки S3 (проблемы доступа/квот).

## 11. Доп. задание: критерии выбора технологии (плюсы/минусы)

| Критерий | ELK (Elastic) | OpenSearch | Splunk | Grafana Loki |
|---|---|---|---|---|
| Лицензия/стоимость | может быть дороже из‑за лицензии | open‑source (Apache 2.0), дешевле | дорого, проприетарно | open‑source |
| Операционная сложность | высокая (кластер, обновления) | высокая/средняя (аналогично) | ниже, но vendor lock-in | ниже (простая модель хранения) |
| Полнотекстовый поиск | сильный | сильный | сильный | ограничен по сравнению с ES/OS |
| Агрегации/аналитика | сильные | сильные | сильные | хорошие, но иной подход (labels) |
| Интеграция с Grafana | возможно | возможно | возможно | нативно |
| Масштабирование | хорошее, но требует опыта | хорошее, требует опыта | хорошее, но дорого | хорошее и часто проще |
| Подходит для «поиск по order_id/trace_id» | да | да | да | да |
| Когда выбирать | если уже есть Elastic-экосистема | если нужен ES‑подобный стек без зависимости от Elastic | если нужен enterprise‑комплект «из коробки» | если важны простота и стоимость, и достаточно label/query‑подхода |

**Выбор для «Александрита» (MVP): OpenSearch + Fluent Bit**  
Причины: быстрый старт, привычный поиск по `order_id`, независимость от коммерческой лицензии, понятная схема индексов и ретеншена.
