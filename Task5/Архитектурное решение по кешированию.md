# Архитектурное решение по кешированию (Task5)

## 1. Контекст и проблема

Основная жалоба операторов: **первая страница MES** (дашборд «заказы в работе по статусам» с фильтром и пагинацией) загружается долго даже после оптимизаций UI.  
Параллельно бизнесу важна скорость прохождения заказа и предсказуемость статусов (чтобы заказы не «висели»).

С учётом C4 и статусов заказа, самый частый и критичный read‑паттерн в MES:
- получить **самые новые** заказы по статусам (обычно top‑N, упорядочивание по `created_at`/`status_changed_at`);
- быстро отдать список оператору (внутренний SLA - секунды).

---

## 2. Что кешируем

### 2.1. Кандидаты на кеширование
1) **Списки заказов для дашборда MES** (по статусам/фильтрам + пагинация).  
2) (Опционально) **результаты расчёта цены** для повторяющихся 3D‑моделей (по хэшу модели + параметрам расчёта).  
3) (Базово, без обсуждений) **статические ресурсы SPA** (CDN/ETag) - но это не решает проблему «список заказов».

### 2.2. Выбор для MVP
Фокусируемся на **(1)**, потому что:
- это напрямую влияет на скорость работы операторов и на throughput производства;
- нагрузка на DB растёт линейно с количеством заказов;
- типовой запрос «список + фильтры + сортировка» деградирует при росте таблиц.

---

## 3. Мотивация

Что даёт кеширование списков заказов:
- **Снижение latency** дашборда MES (p95/p99) → операторы быстрее берут новые заказы.
- **Снижение нагрузки на MES DB** (CPU/IO/locks/connection pool) → меньше деградаций/таймаутов.
- **Стабильность при росте заказов** без немедленного масштабирования DB.
- **Предсказуемость «самые новые заказы»**: отдаём свежий top‑N из кеша, а не ждём тяжёлый запрос.
- **Снижение MTTR**: проще диагностировать (cache hit/miss, обновления по событиям).

Метрики эффекта:
- p95/p99 latency на `GET /orders?status=...`
- cache hit ratio по ключевым статусам
- CPU/Connections/slow queries в MES DB
- среднее время «SUBMITTED → MANUFACTURING_STARTED» (оператор взял заказ)

---

## 4. Предлагаемое решение

### 4.1. Тип кеширования
**Серверное кеширование** (в MES API), потому что:
- данные общие для многих операторов;
- операторам нужна **свежесть**, а client‑cache даёт слабый контроль консистентности;
- можно централизованно управлять TTL/инвалидацией и наблюдать hit/miss.

### 4.2. Хранилище кеша
**Redis** (managed или self‑hosted), как быстрый in‑memory кеш + структуры данных для top‑N.

### 4.3. Паттерн
Для чтения дашборда: **Cache‑Aside** (с TTL) + **программная инвалидация/обновление** при изменении статусов.

Почему не чистый Write‑Through:
- у нас много сценариев изменения статусов, возможны ретраи и «переигрывания» событий;
- проще гарантировать корректность через DB как source of truth, а Redis держать как ускоритель чтений.

Почему не чистый Refresh‑Ahead:
- требует отдельного планировщика и прогнозирования горячих ключей;
- часть ключей (статусы/фильтры) предсказуемы, но проще начать с event‑driven обновления.

### 4.4. Что именно лежит в кеше (минимум)
Ключи вида:
- `mes:orders:list:{status}:p{page}:l{limit}` → JSON списка (order_id, created_at, priority, short fields)
- `mes:orders:latest:{status}` → top‑N (например, Redis Sorted Set по `created_at/status_changed_at`)

TTL:
- для page‑кешей: 10–30 секунд (компромисс свежести и нагрузки)
- для top‑N: 30–120 секунд, но **обновляем программно** при смене статуса

## 6. Стратегия инвалидации кеша

Комбинированная стратегия:

1) **Программная инвалидация по ключу** при изменении статуса заказа:
- при `status_changed(order_id, from, to)`:
  - удалить (или пометить устаревшими) ключи `mes:orders:list:{from}:*` и `mes:orders:list:{to}:*` для первых N страниц (обычно достаточно 1–3 страниц);
  - обновить структуры `mes:orders:latest:{from}` и `mes:orders:latest:{to}` (remove/add).
2) **TTL как страховка**:
- даже если событие потерялось/не дошло, кеш сам протухнет через 10–30 секунд.
3) **Защита от stampede**:
- на ключи ставим «мягкую блокировку» (singleflight) на 1–2 секунды, чтобы при массовых запросах один поток прогревал кеш.

Сравнение стратегий:

| Первая стратегия | Вторая стратегия | Остальные стратегии |
|---|---|---|
| **Инвалидация по событию + TTL** | **Только TTL** | **Только по ключу без TTL** / «всё чистим всегда» |
| Лучше подходит, потому что кеш остаётся свежим при смене статусов и не создаёт лишнюю нагрузку на DB. TTL страхует от потерь событий. | Простая, но при высокой активности операторов будет много cache miss и нагрузка на DB останется высокой. | Без TTL опасно (риск вечной неконсистентности). Полная очистка всего кеша создаёт волны miss и деградацию. |

## 7. Доп. задание: два варианта решения

| Критерий | Решение 1 (рекомендуемое) | Решение 2 (альтернатива) |
|---|---|---|
| Описание | Redis + Cache‑Aside для list‑эндпоинта + event‑driven инвалидация | Денормализация в DB: отдельная таблица/материализованное представление «orders_dashboard» + индексы + ограниченный кеш на 5–10 секунд |
| Диаграммы | см. seq‑*.puml | те же sequence, но вместо Redis - «Dashboard View Table» |
| Плюсы | Быстрое чтение, низкая нагрузка на DB, гибко | Меньше инфраструктуры (можно без Redis), проще консистентность (всё в DB) |
| Минусы | Нужно поддерживать Redis и инвалидацию | При росте объёма таблиц DB всё равно станет узким местом; тяжёлые запросы сохранятся |
| Когда выбрать | Рост заказов и активность операторов уже создают нагрузку | Если запрещены внешние кеши и нужен самый простой infra‑контур |

**Заключение:** для текущей боли MES (скорость дашборда + рост заказов) более подходяще **Решение 1**. Оно разгружает DB и даёт предсказуемую latency. Решение 2 можно использовать как промежуточный шаг, если Redis недоступен организационно.

## 8. План внедрения (коротко)

1) Добавить Redis (managed) и сетевые правила доступа.  
2) В MES API:
   - внедрить слой кеша для `GET /orders` (Cache‑Aside + singleflight);
   - внедрить обработчик `status_changed` (после commit в DB) → инвалидация ключей/обновление top‑N.
3) Добавить метрики: cache hit/miss, время чтения из Redis, время DB‑fallback.  
4) Ограничить payload списка заказов (только поля для дашборда), детали отдавать отдельным запросом.  
5) Протестировать нагрузкой (рост заказов, 10–50 одновременных операторов).
